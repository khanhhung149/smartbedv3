# ESP32 POC Firmware Build: From Zero to Realtime Dashboard

**Date**: 2026-04-10
**Severity**: Medium
**Component**: ESP32 Firmware (ESPAsyncWebServer, WebSocket, UART)
**Status**: Complete

## What Happened

Built functional ESP32 PlatformIO firmware in a single session that reads Legact Pro V2 sleep pad data via UART, maintains realtime connection state, and serves a web dashboard over WiFi. Got the device running at acceptable resource levels (Flash 72.3%, RAM 14.2%) with proper lifecycle management.

## The Brutal Truth

This worked faster than expected because the problem was simpler than a full platform. We didn't have to argue about architecture—just read serial data, buffer it, broadcast it. The real challenge wasn't technical; it was discipline: keeping WiFi reconnection logic clean, preventing buffer overflow on the UART side, and resisting the urge to prematurely optimize the JSON serialization.

The satisfying part: the device actually boots, connects to WiFi via captive portal (no hardcoded credentials), and streams respiration rate changes to a browser in <200ms latency. That felt like proof of concept done right.

## Technical Details

**Stack chosen:**
- ESPAsyncWebServer (async handling, non-blocking WebSocket)
- ArduinoJson (6.x, static buffer for predictable memory)
- WiFiManager (captive portal, auto-retry on failure)
- ESPmDNS (sleeppad.local hostname for convenience)

**Keep-alive protocol discovered:**
- 0x04 command: Monitor mode (enables continuous heartbeat)
- 0x08 command: Heartbeat response (must send every ~30s or pad stops)
- Respiration rate frames: Wrapped in proper response envelope, then rounded to 2 decimals for stability

**Resource utilization:**
- Flash: 72.3% (tight but acceptable for feature set)
- RAM: 14.2% during runtime (plenty of headroom for future MQTT client)
- Latency: <200ms dashboard update on local WiFi

## What We Tried

1. **Raw WebSocket buffering** → Initial attempt leaked memory on disconnect. Switched to managed frame queue.
2. **Hardcoded WiFi credentials** → Rejected immediately. WiFiManager + captive portal added ~8KB flash, worth it.
3. **Continuous keep-alive pings** → Caused frame drops. Fixed by batching keep-alives with data frames.
4. **Full-precision respiration rates** → Dashboard flickered due to sensor noise. Rounded to 2 decimals; stable now.

## Root Cause Analysis

The firmware worked because we followed a clear constraint: **single responsibility**—read pad, broadcast to web. No attempt to store data, no cloud sync, no real-time alerts. This simplicity forced good design decisions:
- Separate UART handler from WebSocket handler (zero coupling)
- Stateless JSON serialization (same frame sent to all clients)
- Simple retry logic for keep-alives (exponential backoff not needed at 30s intervals)

The resource crunch (72.3% flash) revealed our architecture was reasonable but not optimized. The ~8KB WiFiManager overhead is worth the UX; we can't ship captive portal in firmware every time.

## Lessons Learned

1. **Async web frameworks matter.** ESPAsyncWebServer's non-blocking nature prevented the UART handler from starving during client connections. Blocking API would have caused data loss.

2. **Keep-alive protocols are fragile.** The 0x04/0x08 dance with the pad is undocumented proprietary. Discovered through trial and error. Future: document this thoroughly—next developer will struggle.

3. **Memory predictability > micro-optimizations.** ArduinoJson with static buffer (fixed ~2KB) is safer than dynamic allocation for embedded systems, even if slightly wasteful. No surprise OOM at 3am.

4. **Captive portal is non-negotiable UX.** Every user will forget to configure WiFi. WiFiManager solves this without shipping new firmware. The 8KB cost is justified by support burden avoided.

5. **Local mDNS before cloud sync.** sleeppad.local works without internet. Users can test in airplane mode. Start simple, add complexity only when proven necessary.

## Next Steps

1. **Document the 0x04/0x08 protocol** in project wiki. Include command timing constraints. This will haunt us otherwise.
2. **Replace WiFiManager + WebServer with BLE GATT** in Phase 2. WiFi dashboard on ESP32 is POC; production needs Flutter provisioning app.
3. **Add MQTT client** to firmware. Keep this WebSocket code as fallback for local testing only.
4. **Monitor flash usage** going forward. 72.3% is acceptable now but we're adding MQTT (PubSubClient ~10KB). May need to trim something non-essential.
